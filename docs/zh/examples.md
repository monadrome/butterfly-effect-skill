# 示例

下面的案例同时展示来源请求、观察到的纠偏和最终重开产物。示例文字只用于说明格式，实际提示词必须以选定会话中的证据为准。

## 当前会话

调用：

```text
使用 $butterfly-effect 分析当前会话。
```

观察到的纠偏：

- 修改前先分析。
- 必须在指定 worktree 工作。
- 保留 V2，通过开关新增 V3。
- 未明确要求时不要新增测试。

重开提示词：

> 先在指定 worktree 中检查并解释现有行为、调用链和问题原因，不要修改代码。等我确认后再实现。保留 V2，通过默认关闭的开关新增 V3；配置读取留在入口，核心匹配逻辑使用纯函数和显式参数。运行已有测试，未明确要求时不要新增测试；提交和推送前检查 worktree 与 diff。

默认来源就是当前可见的对话，不需要搜索本地会话记录。

## 非编码任务

一次产品定位会话中出现了这些纠偏：

- 从产品第一性原理出发，不要套用热门模板。
- 发布只是使用场景，不是前置条件。
- 修改高影响的发现文案前，先让用户确认。

重开提示词：

> 先确认产品的核心结果、用户动机、触发边界和行为不变量，不要从热门模板直接开始。把发布流程视为常见场景而非必要条件；先给出产品定位和 discovery description 候选，等我明确选择后再修改，并同步保持 Skill、README、package 和 marketplace 文案一致。

## 指定本地会话

调用：

```text
使用 $butterfly-effect 分析 Codex 会话 "checkout-refactor"。
```

Skill 会定位这个本地会话，按时间顺序提取用户与 Agent 消息。除非工具载荷能够解释一次纠偏，否则不纳入分析。Claude Code 会话也可以用同样方式指定。遇到多个相似名称时，优先选择最强的精确匹配；只有这个假设会影响结果时，才需要说明。

## Transcript 或 Handoff

调用：

```text
使用 $butterfly-effect 分析 /work/exports/checkout-review.md。
```

直接路径会按原样读取，并保留消息顺序和说话人信息。分析 Issue 讨论或 Review 线程时，需要先导出内容或提供本地可读路径；Skill 不会自行抓取远端内容。

## Detailed 模式

调用：

```text
使用 $butterfly-effect --detailed 分析当前会话。
```

输出结构：

```markdown
## 重开提示词

> 先检查……

## 已吸收的纠偏

- 分析门槛 -> 修改前先检查并解释。
- 兼容要求 -> 保留旧路径，通过开关接入新路径。

## 未纳入

- 具体根因是后来才查到的，因此改写成检查步骤。
- 一次性的语气反应证据太弱，不作为稳定偏好。
```

重开提示词始终放在最前面。Detailed 模式用于解释映射关系，不能用复盘报告替代提示词。

## 多个会话

调用：

```text
使用 $butterfly-effect 分析这三个会话导出文件，并为每个代表性案例生成独立的重开提示词。
```

先分别分析每个来源，再进行比较。每段提示词都要有清楚的标题，并且能够独立使用。只有重复出现或用户明确要求保留的规则，才能成为跨会话指导；无关的一次性决定仍留在原案例中。

## 后来才发现的事实

假设会话后期才发现生产配置只应用了一部分，不要把它写成开局时已知的事实：

```text
生产配置只应用了一部分。
```

应改成调查要求：

> 提出修改方案前，拉取全部相关生产配置，区分未配置、空值和代码默认值，并沿路由、存储、过滤和最终输出追踪每个配置的实际影响。

## 稳定偏好与一次性决定

证据：

- 用户在多个会话中都要求“修改前先分析”，并明确要求 Agent 记住。
- 某一次会话因为 staging 环境不可用，用户临时要求不要测试。

处理方式：

- 在适用的任务里，把分析门槛作为稳定协作偏好。
- 临时测试限制只进入那次任务的重开提示词，不能概括成“用户从来不想测试”。

## 历史缺失与隐私

如果指定会话无法读取，用一句话说明来源缺失，再仅依据当前仍可见的证据生成结果。不要编造丢失的纠偏。

如果 transcript 中含有 token、客户标识符或无关的个人信息，输出时应删除。相关操作要求确实重要时，可以改写成“使用已配置的服务账号完成认证”，但不能复述具体值或身份。

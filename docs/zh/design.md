# 设计说明

蝴蝶效应是一个事后的轨迹偏斜纠正工具。它分析已经发生的 AI 协作会话，定位 Agent 的行动从哪里开始偏离用户目标，再返回 rewind 建议和更新后的提示词，用于重新开始同一个任务。任务可以是编码、调研、写作、设计、规划、运营或其他工作。

## 产品定位

| 原则 | 含义 |
|---|---|
| 零准备 | 直接使用已经存在的会话记录，不要求事先安装追踪器、hook 或标记每次纠偏。 |
| Rewind-first | 先返回有证据支持的最早偏斜边界及其与纠偏链的关系，再返回可直接用于新会话的提示词；分析依据只在 `--detailed` 模式下作为辅助信息出现。 |
| 反事实重开 | 追问用户最初应该怎样描述任务，同时尊重当时真正可知的信息范围。 |
| 领域中立 | 保留任务自身的受众、产物、证据标准和验收条件，不把编码场景的默认规则带入其他领域。 |

零准备不等于没有输入。Skill 仍然需要当前可见的会话、能够定位的会话名称，或用户提供的 transcript 路径。已经丢失的历史无法凭空还原。

## 证据模型

同一句用户要求放在不同上下文里，可能属于不同的证据类型。

| 证据 | 在重开提示词中的处理方式 |
|---|---|
| 重复出现的偏好，或明确要求记住的规则 | 与当前任务相关时，作为稳定偏好纳入 |
| 能够避免返工或保护重要不变量的纠偏 | 直接写成任务专属要求 |
| 最终结果仍保留的一次性改向 | 只用于这次重开，不扩展成用户画像 |
| 调查后才发现的事实 | 改写成检查、复现或验证指令 |
| 后来的决定推翻了较早的指令 | 在相同阶段和范围内采用最新明确决定 |
| 偶然的领域细节或缺乏依据的性格推断 | 删除，或概括成背后的真实意图 |

项目规则和已经接受的最终决定也可以支撑提示词条款。能读取原始消息时，自动生成的摘要只能作为次级证据。

## 轨迹偏斜与 Rewind 模型

分析单位不是孤立的用户消息，而是一条纠偏链。纠偏链把 Agent 的假设或行动、用户的一次实质纠偏，以及后续修复同一目标、受众、产物或验收条件的纠偏连接起来。

rewind 点是导致大部分相关纠偏的最早 Agent 假设或行动，不是自动取第一条用户纠偏。证据足够时，可以写成 `before turn <id>`、`before <timestamp>`、`before the Agent assumed ...` 或 `the original request`。如果存在多条独立链，应分别报告边界；如果早期历史缺失或因果关系不足，则返回 `No reliable drift or rewind point detected`，不能编造位置。

更新后的提示词要保留仍然有效的早期决定，并把后见信息改写成检查要求。它必须能够避免对应的纠偏链，但不能把后来才发现的根因直接断言成开局事实。

## 重建顺序

1. 还原原始目标和第一轮对话时可用的信息。
2. 按时间顺序建立 Agent 假设、行动、纠偏、已接受决定和后续发现组成的时间线。
3. 找出真正改变做法的纠偏，将它们连接成因果链，并为每条链定位最早有依据的偏斜边界。
4. 判断每条纠偏的置信度、适用范围和持久性。
5. 按执行顺序写出 rewind 建议和更新后的提示词。
6. 用每条高置信度纠偏反查提示词是否覆盖，并说明历史缺失或歧义。

最终提示词必须可以脱离复盘独立使用。新的 Agent 不应依赖旧会话，才能理解目标、决策门槛、执行约束和验收要求。

## 后见信息边界

用户在任务开始时本来就可以说明的要求，可以直接进入提示词。任务过程中才发现的原因、隐藏依赖、来源局限或环境约束不可以。

后来发现：

```text
来源数据只覆盖了一个地区。
```

反事实重开条款：

```text
下结论前，先验证来源覆盖范围和地区范围。
```

这样既保留了纠偏带来的经验，也没有伪造先验知识，更不会在验证前过早指定具体解法。

## 矛盾与置信度

同一阶段、同一范围内发生冲突时，以较晚的明确决定为准。较早的指令仍可能在其他阶段成立。例如，“暂时不要定稿”在用户后来批准发布后，可以保留为审查门槛，而不是永久禁止发布。

明确说出、重复出现、被最终结果接受，或有项目规则支持的纠偏，置信度较高。一次性的情绪反应和推测出来的性格偏好不属于高置信度证据。证据不足时，应删除该条款，或只把它写成当前任务的要求。

## 非目标

- 蝴蝶效应不是会话记录器。它在有价值的历史已经存在后工作。
- 它不是持久记忆。跨会话偏好需要重复证据，或用户明确要求记住。
- 它不是通用提示词优化器。每个新增条款都必须来自观察到的纠偏或权威项目上下文。
- 它不是以报告为主的复盘工具。默认交付物是简洁的 rewind 建议和更新后的提示词。
- 它不会让新的 Agent 变成全知视角。未知事实仍然需要调查。

## 反事实验证

返回提示词前，逐项检查：

1. 按照这条指令执行，能否避免或明显减少对应的纠偏？
2. 这条信息在开局时是否可知；如果不可知，是否已经改写成调查任务？
3. 提示词是否保留了原始目标，而不是为了回避不确定性缩小任务？
4. 每个约束是否都有证据？
5. 重复条款能否合并，同时不丢失行为要求？

## 常见失败方式

| 失败方式 | 后果 | 防护方式 |
|---|---|---|
| 用 transcript 摘要代替原始消息 | 纠偏顺序或说话人可能丢失 | 优先读取按时间排列的用户与 Agent 消息 |
| 把所有要求都当作纠偏 | 提示词变成会话摘要 | 只保留暴露或改变先前做法的轮次 |
| 把一次反应当成稳定偏好 | 提示词过度拟合用户 | 要求重复证据、明确记忆意图或最终接受 |
| 把后来查到的根因写成已知事实 | 重开提示词泄漏后见信息 | 改写成检查或验证步骤 |
| 把第一条用户纠偏当作 rewind 点 | 建议回退得太晚，原始偏斜仍然存在 | 沿纠偏链向前追溯到更早的 Agent 假设或行动 |
| 先输出长篇分析 | 用户还要自己把报告翻译成指令 | 先放简洁的 rewind 建议和更新后的提示词 |

## 评估方式

仓库检查能够验证静态契约、引用、插件清单、语言边界、发布 tag 和包内容，但不能证明模型提取纠偏的准确率。

行为评估应在新鲜上下文中使用未经加工、纠偏密集的 transcript，并覆盖单一共同偏斜、多条独立纠偏链、早期历史缺失和没有实质偏斜等场景。不要提前提供期望提示词或目标分类。检查结果是否定位最早有依据的边界、覆盖所有高置信度纠偏、排除无依据的推断、保留原始目标，并把后来发现的事实转换成检查要求。只有观察到真实失败模式后，才应增加对应的回归样例。
